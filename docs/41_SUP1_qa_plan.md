## 1. 方針

1 名開発のため「独立した QA 担当者」は存在しない。
**品質保証の実体は CI ゲートとチェックリストである**と定義し、人間の記憶と注意力に依存させない。

| ASPICE が期待すること | 本プロジェクトでの実現手段 |
|---|---|
| 成果物の客観的評価 | CI の自動チェック（lint / guard / test / build） |
| 独立性 | `main` への直接 push 禁止。全変更を PR にし、AI レビュー（`/code-review`）を通す |
| 不適合の追跡 | GitHub Issues（`bug` ラベル）。CI 失敗はマージ不可として物理的に阻止 |
| プロセス遵守の確認 | PR テンプレートのチェックリスト |

## 2. 品質ゲート

| ゲート | タイミング | 判定 | 不合格時 |
|---|---|---|---|
| **G1: CI** | 全 PR | lint / guard / test / build が全て green | マージ不可 |
| **G2: セルフレビュー** | 全 PR | PR テンプレートの全項目にチェック | マージ不可 |
| **G3: AI レビュー** | 全 PR | `/code-review` を実行し、指摘を解決または理由付きで却下 | マージ不可 |
| **G4: 結合テスト** | 機能追加を含む PR | 関連する `IT-*` を実行し結果を PR に記載 | マージ不可 |
| **G5: 実機ゲート** | リリース時 | `DOC-30 §5` の絶対ゲートが全て合格 | リリース不可 |

## 3. 静的チェック項目

### 3.1 自動（CI の `lint` / `guard` ジョブ）

| # | チェック | 実現方法 | 根拠 |
|---|---|---|---|
| S1 | コード整形 | `clang-format --dry-run -Werror`（`.clang-format` に準拠） | 可読性 |
| S2 | **CAN 送信 API の混入禁止** | `twai_transmit` `twai_transmit_v2` の文字列がソースに存在しないこと | `RSK-06`, `SYS-07` |
| S3 | **自己テストモードの指定禁止** | `TWAI_MODE_NO_ACK` が存在しないこと（NORMAL は `DEC-04` により正当。`NO_ACK` は ACK を返さず `RSK-10` を再発させる） | `RSK-10` |
| S4 | ドメイン層の依存分離 | `lib/rusefi_can/` `lib/signal_model/` に `Arduino.h` `esp_` `freertos` `lvgl.h` の include が無いこと | `DEC-06`, `SWR-10` |
| S5 | マジックナンバー禁止（CAN スケーリング） | `lib/rusefi_can/src/` に `0.0001` `0.0333` 等の直書きが無いこと（`rusefi_can_spec.h` の定数のみ使用） | `SWD-01 §1.3` |
| S6 | コンパイラ警告 | `-Wall -Wextra` で警告 0 件 | — |
| S7 | 実行時動的確保の抑制 | `src/` `lib/hal/` `lib/ui/` に `new ` `malloc(` が無いこと（LVGL 内部と起動時確保の明示的許可リストを除く） | `DOC-21 §6` |

### 3.2 手動（PR チェックリスト）

- [ ] 変更に対応する要求 ID をコミットの `Refs:` 行に記載した
- [ ] 要求を変更した場合、先に文書 PR をマージした（`DOC-40 §5`）
- [ ] 新規・変更したドメインロジックに `UT-*` を追加した
- [ ] `DOC-50` トレーサビリティ表を更新した
- [ ] 安全に関わる変更（鮮度管理・CAN 送信・警告表示）を含む場合、該当する `IT-*` を実行した
- [ ] 依存ライブラリを更新した場合、`QT-03`（FPS）を再実行し結果を記載した
- [ ] `docs/` の `最終更新` 日付を更新した

## 4. コーディング規約

| 項目 | 規約 |
|---|---|
| 言語 | C++17 |
| 整形 | `.clang-format`（ベース: Google、インデント 4、列幅 110） |
| 命名 | 型 `PascalCase` / 関数・変数 `camelCase` / 定数・マクロ `UPPER_SNAKE` / メンバ変数 `m_` 接頭辞 |
| ファイル名 | `snake_case.cpp` / `snake_case.h` |
| ヘッダガード | `#pragma once` |
| 例外 | 使用しない（`-fno-exceptions`） |
| RTTI | 使用しない（`-fno-rtti`） |
| `assert` | ドメイン層でのみ使用可。HAL / UI では使わず、エラーを値で返す |
| コメント | **「何を」ではなく「なぜ」を書く**。特に `DOC-*` の要求 ID・設計判断 ID を参照する |
| 単位 | 変数名に単位を含める（`egtC`, `timeoutMs`, `lambdaRaw`）。無単位の数値名を作らない |

## 5. 文書の品質基準

| 基準 | 内容 |
|---|---|
| D1 | 全要求が一意の ID を持ち、ID を再利用していない |
| D2 | 全要求が検証可能（数値または明確な合否条件を含む） |
| D3 | 全要求が上位 ID と検証 ID を持つ（`DOC-50` で孤立が 0 件） |
| D4 | 設計判断には代替案と選定理由が併記されている |
| D5 | 未確定事項は `OPN-*` として明示され、放置されていない |
| D6 | 外部仕様（rusEFI）の記述には一次情報源が明記されている |

## 6. 不適合の扱い

| 重大度 | 定義 | 対応 |
|---|---|---|
| **Critical** | 誤った値を正しいものとして表示する / CAN バスへ送信する / 走行中にフリーズする | 即座に Issue 作成。修正するまで実車使用を中止 |
| Major | 機能が動作しない、要求を満たさない | 次リリースまでに修正 |
| Minor | 見た目の崩れ、利便性の問題 | バックログ |

Critical に該当する不具合が見つかった場合、**原因分析に加えて
「なぜ `UT-*` / `IT-*` で検出できなかったか」を Issue に記載し、テストを追加する**。
テストを追加せずに Critical を閉じない。
